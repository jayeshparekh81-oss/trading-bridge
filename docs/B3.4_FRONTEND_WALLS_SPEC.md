# B3.4 — Frontend upgrade walls (spec, no code) — UX-only

**Goal:** show "upgrade to unlock" UI on premium surfaces, **reactively** driven by backend signals (not by `plan_status` proactively), so nothing locks while `PAYWALL_ENFORCED` is OFF. Backend (B3.2/B3.3) remains the source of truth; this layer is cosmetic. Risk: **Low** (no backend behavior).

## New component(s)
- `frontend/src/components/billing/upgrade-wall.tsx` (or `paywall-gate.tsx`) — a presentational "Premium — upgrade to unlock" block with a CTA → `/pricing`. Variants: full-page wall + inline panel placeholder.
- Optional small hook `useEntitlement()` reading `plan_status` / `plan_tier` from the existing `/api/users/me` (`UserResponse`, fields added in B3.0) — for **labeling only** (current plan, CTA copy), never to gate.

## Where it mounts (premium surfaces from the recon)
- `frontend/src/app/(dashboard)/analytics/page.tsx` — on `402` from `GET /api/users/me/trades/stats` (+ `/me/trades`).
- `frontend/src/app/(dashboard)/trades/page.tsx` — on `402` from `GET /api/strategies/executions`.
- `frontend/src/app/(dashboard)/marketplace/[id]/page.tsx` — Transparency Ledger panel, on `402` from the ledger endpoints.
- `frontend/src/app/(dashboard)/strategies/[id]/backtest/page.tsx` — the advanced panels (`reliability`/`truth`/`regime`/`deviation`/`trade_quality`/`diagnosis`/`health_card`): render the inline upgrade placeholder when that section is **`null`** in the backtest response (B3.3), while the basic result renders normally.

## Reactive trigger contract (the key design)
- **402 `PLAN_REQUIRED`** ⇒ render the wall for that surface.
- **null premium section** (backtest) ⇒ render the inline placeholder in that panel.
- **Never** gate purely on `plan_status` from `/me` — that would lock the UI even while the flag is OFF (backend returns 200/full ⇒ no wall). `plan_status` is for labeling only.

## Response / field changes
- Frontend types: extend the user/profile type with `plan_status`, `plan_tier`, `plan_expires_at` (already returned by `/me`).
- Backtest result type: the advanced sections are already optional client-side (verify); ensure panels handle `null`.

## ⚠️ Critical frontend risk — the api client must treat 402 as paywall, NOT as auth-failure
- **Verify during build:** how `frontend/src/lib` api-client handles non-2xx. If `401` triggers a logout/redirect, ensure **`402` does NOT** — a `402 PLAN_REQUIRED` must surface to the page as a paywall signal, not log the user out or show a generic error toast. This is the single highest-risk integration point.

## Tests
- Component test: renders content on 200; renders the wall on a 402 `PLAN_REQUIRED`; renders the inline placeholder when a backtest section is `null`.
- Flag-OFF behavior (backend returns 200 / full sections) ⇒ **no wall** anywhere (the UI must be invisible until enforcement is on).
- Use the repo's existing frontend test setup (eslint/tsc are gated; check for an RTL/jest harness — if none, at minimum tsc-clean + a Storybook/manual note).

## Risks
- Reactive-not-proactive is mandatory (else UI locks while flag OFF).
- 402-vs-401 handling in the api client (above) — get this wrong and a paywall looks like a session expiry.
- Pure UX; no backend, no migration, no sacred touch. Lands after B3.0's `/me` fields are deployed (so `plan_tier`/`plan_status` are available) — but since walls are reactive to 402/null, it functions even before the flag flip (just never triggers).
